# Harden Dev Rails

Bring an existing project onto the current rails. `setup-dev-rails` covers a
freshly generated project; this covers one that predates the rails or has
drifted off them.

The mechanical part is a script — `nox -s rails`, or `check_rails.py` from
`grmhay/pythonproject`. Run it first and let it produce the worklist. This skill
covers what the script cannot decide.

## Step 0: Find out what is actually wrong

```bash
nix develop --command nox -s rails    # if the project already has the session
# otherwise, from a pythonproject checkout:
nix develop --command python3 rails/check_rails.py /path/to/project
```

Work its failures in the order below. Do not fix what it did not report.

## Step 1: Measure before you enable anything

**Never turn on `strict = true` and then discover the backlog.** Measure it:

```bash
nix develop --command mypy --no-install-types --strict noxfile.py tests <package>
```

Then break the number down before deciding anything:

```bash
# by file, and by error code
grep -o '^[^:]*' errors.txt | sort | uniq -c | sort -rn
grep -o '\[[a-z-]*\]$' errors.txt | sort | uniq -c | sort -rn
```

The split matters more than the total. A four-repo sweep found 0, 8, 8 and 143
errors — and the 143 was the *easiest* of them, because 139 were missing
`-> None` on test functions. Report the breakdown to the user before starting,
not just the count.

## Step 2: Separate mechanical from substantive

`no-untyped-def` on test functions is mechanical. Everything else deserves
reading.

Annotate the mechanical ones with an **AST pass, not a regex**: only add
`-> None` to functions that neither `return <value>` nor `yield`. Walk the tree,
collect the safe ones, patch from the last line backwards so line numbers stay
valid, and print the ones you skipped so you can type them by hand. Fixtures
that return or yield need real types (`Iterator[Session]`, `CliRunner`,
`MagicMock`), and getting them wrong is how you paper over a bug.

**The residue is where the real defects are.** In one sweep the handful of
non-mechanical errors turned out to be: five methods returning an unchecked
`Any` from `resp.json()` where the signature promised `dict[str, Any]`; a name
referenced through a module that merely imported it, which `no_implicit_reexport`
exposed; and a `Row`/`tuple` comparison that could never be equal. Slow down on
these — they are the reason the exercise is worth doing.

## Step 3: Pick the CI gate variant empirically

Two variants are in use, and which one a repo needs is a fact about the repo:

```bash
nix build '.#default' -L        # preferred: also exercises packaging
nix develop --command nox       # fall back to this
```

**Try `nix build` first.** If it fails with `Missing dependencies:
setuptools-scm>=8`, the project has `dynamic = ["version"]` but no
`setuptools-scm` in the flake's `build-system`. Either fix the flake (add it,
plus `env.SETUPTOOLS_SCM_PRETEND_VERSION`, since a flake source carries no
`.git`) or use the devShell variant — and record which, and why, in a comment on
the job.

Gate the publish on it: `build-and-push` must `needs:` the gate job. A gate that
runs *alongside* the publish stops nothing. Two services in this fleet ran nox
in CI while publishing from a job that did not depend on it, and a third had a
second, ungated publish path in a different workflow — `needs` cannot span
workflows.

## Step 4: Order the commits by dependency

Land each concern separately, and land a fix *before* whatever depends on it. If
you fix a flake so `nix build` works and then switch CI to use it, the flake
commit goes first — otherwise the middle of the branch is broken and its message
justifies a choice that is about to be reversed.

If you have already committed in the wrong order and have not pushed, reset and
recommit rather than leaving a misleading commit in the history.

## Step 5: Verify with the real command

Run the exact command CI will run, not a proxy for it. `nox` passing locally
does not prove `nix build '.#default' -L` passes — different environment,
different resolution.

Re-run `nox -s rails` at the end and confirm it is clean.

## Step 6: Adopt the checker

Add the `rails` session and the flake input so the project keeps itself honest:

```nix
pythonproject.url = "github:grmhay/pythonproject";
# ...
railsChecker = pythonproject.packages.${system}.check-rails;
```

Put `railsChecker` in both the devShell and `nativeCheckInputs`, so the session
behaves the same under `nox` and inside `nix build`. Add the `rails-check`
reusable workflow too — it runs the canonical checker independently of anything
this repo can edit.

Do not vendor a copy of `rails/`. A local copy drifts, which is the failure the
checker exists to catch.

## Cautions

- **Check for other agents in the working tree before you start.** A shared
  checkout can have another session mid-refactor; `git status` plus file mtimes
  will tell you. If the tree is already dirty with work that is not yours, do
  not "fix" its failures — commit only your own files and say so.
- **Do not weaken a rule to make it pass.** If the ruff backlog is large, size it
  with `nox -s check -- --stats` and tell the user the number. Narrowing the
  rule list to go green is the drift this is meant to reverse.
- **The docs are part of the change.** If a project claims something in
  `CLAUDE.md` that you did not make true, either make it true or fix the claim.
  Every repo in this fleet claimed "mypy strict is enforced" while none enforced
  it.
